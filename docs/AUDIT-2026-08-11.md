# NST Control Tower — Project Health Audit
**Date:** 2026-08-11
**Auditor:** Mavis (senior engineer, no-BS mode)
**What this is:** A blunt, evidence-based health check. No sugar, no polish. Everything below is reproducible from `curl`, `git log`, and the source.

---

## TL;DR — The Water Is Not Coming, The Water Is Here

**Live site: stale (18 days behind main).** Last successful deploy to production was **before 23 July 2026**. The latest commit on `main` (7368475, 24 July) has not reached production. Every commit since then — your "live" site — is a build from before the 3D terrain, water-balance, sensor-situation-board, and Rams × NYCTA token system work landed.

**CI is red. Deploy is skipped. Nobody is paged.** Test workflow has been failing on main for at least 4 consecutive pushes (commits 7368475, 006b6ce, 5b927de, 1ea0f37). Deploy workflow correctly gates on Test success, so it has been `skipped` every time. There is **no notification, no Slack hook, no cron reminder** watching this. The deploys silently stop, the live site goes stale, and you ship the next batch of code on top of a dead branch.

This is the #1 problem. Fix this first. Everything else is polish.

## The Five Findings, Ranked by Severity

### 🔴 1. CI is red and the deploy pipeline is dead (P0)

| | |
|---|---|
| **Symptom** | Every commit to main since 23 July has failed Test, so every Deploy was skipped. Live site is stuck on a build from before 23 July. |
| **Evidence** | `gh api repos/Nonarkara/nst-control-tower/actions/runs` shows Test=`failure`, Deploy=`skipped` for the last 4 runs. |
| **Why nobody noticed** | No CI status badge in README, no Slack/Feishu ping on test failure, no cron that checks "is production > 24h behind main?" |
| **Fix** | (a) Find out *why* test is failing. (b) Add a `mavis cron` self-reminder that fires every 30 min if `commits ahead of prod > 5`. (c) Add a Test status badge to README that turns red on failure — shame is a feature. |

The most likely cause of test failure: **E2E tests need a live API but the CI workflow only starts the Vite dev server, not the Hono API**. Either start the API in CI or relax the smoke tests to skip API-dependent assertions. The current setup will fail every run.

### 🟠 2. The air-quality adapter silently degrades for an hour when its first upstream response is empty (P1)

| | |
|---|---|
| **Symptom** | `GET /api/air-quality` returns `features:[]` with `fallbackTier: "scenario"` — even though Open-Meteo is returning valid AQI data right now. |
| **Evidence** | Three consecutive `curl` calls all returned empty. Direct Node `fetch` to the same URL returned `us_aqi: 47` with `time: "2026-08-11T13:00"`. The adapter and the upstream agree; the API doesn't. |
| **Root cause** | `apps/api/src/adapters/airQuality.ts` wraps the upstream call in `cached("air-quality", 3600, ...)`. The Cloudflare Workers isolate's cold-start request can land during a brief upstream hiccup, gets an empty `current:{}` back, and the empty NormalizedFeed is cached for 1 hour. Every subsequent call returns the cached empty feed — for 1 hour. |
| **Test smell that documents the bug** | `apps/api/src/adapters/airQuality.test.ts` lines 19–42: tests 1 and 2 are **order-dependent**. Test 1 mocks an empty response, test 2 asserts the cache still holds it. Vitest runs in file order so this passes, but it documents the production bug. The tests are not just fragile — they are a *postmortem in the source*. |
| **Why it matters** | The AQI badge is one of the most visible panels on the dashboard. For the mayor's office during a haze event, an hour of false "Unhealthy" → "Unavailable" oscillation is reputation damage. |
| **Fix** | (a) Reject `fallbackTier: "scenario"` as a cacheable value when the upstream actually succeeded (check `current` non-empty, not just `200 OK`). (b) Add `c.us_aqi == null && c.pm2_5 == null` as a "do not cache" guard. (c) Rewrite the tests to be order-independent (use `vi.resetModules()` between every test). |

### 🟡 4. Bundle is 2.6MB minified, no code splitting on the main route (P2)

Don't ship a sidebar with 9 features where 4 will always be empty. That's a UX lie.

## What's Actually Working (don't break this)

✅ **Adapter pattern is sound.** Every feed is a `NormalizedFeed<T>`, the cache is in-memory with stale-while-revalidate, and the `meta.fallbackTier` is propagated all the way to PanelHeader. This is the right design and you should not change it.

✅ **Data honesty is real.** Every empty result is labeled with `fallbackTier: "scenario"`, `unavailable`, or `reference`. The PanelHeader renders the tier. The AqiBadge shows "Unavailable" with a skeleton instead of a fake "47". The WorldStrip renders "—" for null values. The system does not lie.

✅ **Core flood surveillance is operationally excellent.** HII ThaiWater water-level (51 stations, 10-min updates), HII rainfall (143 stations, 1h + 24h), DWR EWS (86 stations, official 0-3 alert status), RID reservoirs (4 in NST), WRF-ROMS 3-day forecast, Air4Thai PCD stations, news, HII water-balance. These are the things that matter when the rain starts and the water rises. They are real, they are live, they are the lead indicators for the Tha Dee / Pak Phanang cascade.

✅ **Rams × NYCTA design DNA is followed.** tokens.css enforces `border-radius: 0 !important`, no shadows, no blurs. The accent is exactly the design-core's `#1f6e43`. The route palette (--rt-blue, --rt-orange, etc.) is the closed NYCTA 8-color set, enclosed-use only. CollapsibleSection with localStorage persistence. The design is in good shape.

✅ **Test coverage is wide.** 1,220 unit tests across 73 files, 20 Playwright E2E smoke tests. The unit tests pass locally. The failure is in CI, not in the tests.

✅ **Type safety.** All three packages typecheck clean.

## Smaller Stuff (P3, but real)

### A. Source catalog shows 71 sources but only 30 are "live". UI doesn't say "30 of 71".

When you open the SOURCES modal you see "70 cataloged data sources (27 live today)" — except it says 71 / 30 now and the string is stale. The SourceCatalog has a status filter with `live | ready | planned | research | stub` but the **stub** status is never set by any source (it's a defensive enum value, not used). This is OK but it's a small lie by omission — a stub value nobody emits.

### B. Two adapter unit tests are order-dependent

`apps/api/src/adapters/airQuality.test.ts` tests 1+2 depend on file execution order to work. `apps/api/src/adapters/weather.test.ts` likely has the same pattern. **Vitest by default runs in file order, so this works, but it's a CI time bomb** the day someone enables `--shuffle`. Fix with `vi.resetModules()` and a fresh import per `it()`.

### C. `air-quality/aqicn` and `air-quality/air4thai` are two endpoints that do the same thing

`/api/air-quality` (Open-Meteo grid, no key) and `/api/air-quality/air4thai` (PCD, no key) are both wired. Plus the unwired `/api/air-quality/aqicn` (AQICN, needs key). Three AQI sources for one badge. The user sees the AqiBadge in the World Strip + the main panel. The trend endpoint is `/api/air-quality/trend`. Decide which is the canonical AQI source for the city — Air4Thai (Thai PCD ground truth, no key) is the obvious choice — and either deprecate or annotate the others.

### D. The AqiBadge has two duplicate sources in props

`AqiBadge` takes a `trend` prop and a `loading` flag. In `App.tsx` it gets `trend={aqiTrend.data[0] ?? null} loading={aqiTrend.fallbackTier === "loading"}`. **The `loading` prop is unreachable in practice** — the useFeed hook never sets `fallbackTier: "loading"`, it sets `"scenario"`. The condition is dead code that the badge code already handles via `loading || !trend`. Remove the prop or fix the hook to use it.

### E. `useFeed` in `apps/web/src/hooks/useFeed.ts` is the right abstraction but it doesn't propagate `fallbackTier` cleanly

It exposes `data`, `error`, `loading` but treats `fallbackTier` as second-class. Looking at App.tsx line 1811, the code does `aqiTrend.fallbackTier === "loading"` — but `useFeed` never returns a fallbackTier of `"loading"`. So this is always `false` and the badge is always either loading or has a value. The contract needs to be tightened.

### F. The `e2e/smoke.spec.ts` config is "Chonburi" branded

Already mentioned. `playwright.config.ts` line 5 comment.

### G. CHONBURI is a legacy alias for NST, but the symbol name is everywhere

`apps/web/src/lib/apiBase.ts` has a `LEGACY_API_HOSTS` set that includes 4 old Chula/Chonburi/Yala API hosts. Half the adapters use `CHONBURI.center` instead of `NST.center`. Both work, but the codebase's mental model has an alias pretending to be the primary. Pick a name. (My vote: `NST` for everything, delete the `CHONBURI` export.)

### H. The `SourceCatalog` "stub" status

Defensive enum value never used. Either remove it or use it for a real "we have the route registered but the upstream is permanently down" case (e.g. CCTV if you give up on Longdo for NST).

### I. The SheetsPanel button's API route

`/api/sheets` returns 404, but that's fine because SheetsPanel is purely client-side (localStorage + iframe). The topbar "SHEETS" button works. No action needed, but it confused me for 30 seconds during the audit, so document this somewhere.

### J. The Terminal Dashboard is a separate "System B" 

`Root.tsx` flips between `geo` (App) and `terminal` (Bloomberg-style Watch Terminal) via a button. The terminal is its own concern — it has hardcoded hex colors (`#10B981`, `#F1BE48`, etc.) and `any` types in the data hook. It's a separate feature flag, not a core dependency. **Don't break it while fixing the main app.** If you have time, the `any` types in `TerminalDashboard.tsx` (14 of them) are the worst type hygiene in the codebase. But the file is independent.

### K. The bundle has 2.6MB of "index" + many small lazy chunks

The lazy chunks are right-sized (3-50KB each). The 2.6MB main is the offender. (See finding #4.)

### L. The dashboard's name in the title bar

`NST-01 · Nakhon Si Thammarat City Municipality` — clean, on-brand. No fix needed.

### M. The `dist/assets/` directory after `pnpm build` is 39MB

Includes source maps (9MB+). Fine for development; Cloudflare will serve the gzipped JS at 771KB on the wire. But the source map files shouldn't be deployed. The wrangler config doesn't say `exclude: ["**/*.map"]` — check if those are being uploaded.

## What I Would Do Today (in this order)

1. **Fix CI.** Run `pnpm test:e2e` locally in CI mode and see what fails. If it's the missing API, either start the API in CI or skip API-dependent smoke tests. Once Test is green, Deploy will run. The live site is **18 days behind** — getting it caught up is the highest-leverage thing you can do right now.

2. **Fix the air-quality stale-empty-cache bug.** Add a guard: if `current` is empty or `current.us_aqi == null`, throw instead of returning an empty feed. This forces the cache to fall back to the outer try/catch → "scenario" → next refresh re-attempts. 5 lines of code. Then rewrite the two affected unit tests with `resetModules()`.

3. **Set up a cron that watches the live site.** `mavis cron self every 30m` that hits `/api/health`, checks `git log -1 origin/main` vs `git log -1 HEAD` and `wrangler pages deployment list`, and pages you if prod is > 1 day behind main. The "I am still seeing the old version" problem is a **detection** problem, not a deploy problem. Fix the detection.

4. **Bump the README.** 1,168 → 1,220 tests. 18 → 20 E2E. 27 → 30 live sources. "Chonburi" → "NST" in the Playwright config comment.

5. **Tell the truth in the sidebar.** For the 5 adapters that will never have NST data (ITIC, city-reports, GloFAS cascade, flights, markets), either annotate them as "Bangkok-only" or "needs key" directly in the lens sidebar so the user knows the lens is a *demo*, not live data.

6. **Code-split the heavy panels.** `React.lazy` the 5-6 heavy 3rd-party panels. This is a half-day and it gets first-paint under 2 seconds on phone. The control tower has to load fast in a crisis.

7. **Add a "live deployment" badge to the topbar** — a tiny "v1.4.3 · deployed 5 min ago" line. If the user can see the version, they can see when they're looking at a stale build. Right now the only way to know the build is old is to compare a hash.

## Closing

This is **not a bad project.** The adapter pattern is right. The data contract is right. The design system is right. The core flood surveillance is operationally excellent — 51 river gauges, 143 rain stations, 86 flash-flood EWS stations, 4 reservoirs, 3-day WRF forecast, all live. When the water comes to Nakhon Si Thammarat, the dashboard will tell the mayor where it's coming from and where to send the trucks.

But the **delivery system is broken**. The live site is 18 days stale because CI is red and nobody noticed. The air-quality panel shows "Unavailable" for an hour every time the isolate cold-starts. The README is 50 tests behind the truth. The bundle is 2.6MB. These are not deep architectural problems — they're the last 10% of operational maturity that every serious project has to grind through.

Fix CI. Fix the air-quality cache. Set up detection. The water is coming, and the data is good. Just ship the build.
